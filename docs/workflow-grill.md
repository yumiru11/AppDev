1. **工作流本质**：「规格驱动 + 增量交付」——合法性建立在「规格完备 + 执行正确」两个前提上——**两个前提都不成立，且工作流没有检测机制**

5. **爆炸半径**：GitLight 2 模块 vs AppDev 25 模块——同样偏差的爆炸半径是 **12 倍**

## 一、真机验收时机与频率

### 1.1 真机验收应该在哪个环节发生？

**背景**：你亲测原型这一周，发现问题的速度远快于任何代理/测试——但「你亲自测」不可扩展（后续 11 票 + 25 模块）。什么时候测、测什么，直接决定返工量。

**选项展开**：
- **A. 每票合入前必真机验收**——票做完 → 你装机测关键路径 → 过了才合 main。代价：你的时间 = 每票 30-60 分钟；收益：问题发现最早、返工最小。原型阶段实测有效（7 问题当场修）
- **B. 里程碑式走查**——攒 2-3 票合入后一次性走查。代价：问题堆积、连坐返工（GitLight 模式）；收益：你的时间少
- **C. 分级验收**——★ 票代理自验 + 截图证据；★★★ 票你真机验收；全局感受（导航/主题/图标）里程碑走查
- **D. 验收卡机制**——每票附带「验收卡」（3-5 条可执行的真机操作 + 预期），你照卡测，代理按卡收尾

**联想参照**：GitLight 死在 B；原型阶段是 A（效果最好但不可扩展）；GitHub/大厂用「设计走查会」（批量、聚焦、有清单）≈ C+D 结合。

### 1.2 你不在的时候（睡觉/上班），真机验收怎么兜？

**背景**：你亲测需要你在场——代理跑票是 24h 的（云端/夜跑），验收环节会变成瓶颈。

**选项展开**：
- **A. 代理自验 + 证据链**——代理装机自测（adb 操作 + 截图 + logcat），产出「验收证据包」，你醒了只看证据包
- **B. 信任票面 + 风险标注**——代理按 tickets 验收标准自验，拿不准的标「需真人确认」挂起，不阻塞其他票
- **C. 只跑无感票**——你不在场时只跑「纯逻辑票」（数据层/Repository），UI 票等你回来
- **D. 截图基准回归**（把截图工具调研落地后）——UI 票自动截图对比基准，偏差即挂起

**联想参照**：本轮原型我 adb 装机 + 抓 logcat 验证（WebView 诊断/徽章尺寸）——代理自验可行但**有限**（行为层还是要你）；云端 AI 跑票时「停手报告」机制已有（dsh-guide）。

## 二、体感规格化——「脑内效果」怎么写进验收标准

### 2.1 体感层能不能规格化？写到什么粒度？

**背景**：你说过「体感层无法文字化」——但原型证明「眼见为实」最快。UI 票开工前 grill（#127）已经让「脑内效果」提前暴露——问题是 grill 出的结论怎么变成可验收的规格。

**选项展开**：
- **A. 文字规格 + 截图锚点**——grill 结论写成「对比锚点」：以 GitHub 网页/参考 app 的某截图为准（如「列表间距对齐 GitHub 网页手机版」）——代理看图执行，不猜文字
- **B. 原型先行**——复杂 UI 票先做交互原型（像 README 原型）你看过再写实现票——成本高（每票多一轮）
- **C. 验收标准只写「可观察行为」**——不写「好看」写「顶栏高度 56dp、间距 16dp、圆角 12dp」（数字规格）；「好看」留给真机走查
- **D. 双层规格**——「硬规格」（数字/行为/状态，代理必须达标）+「软规格」（观感/氛围，写清参考物，真机走查兜底）

**联想参照**：ui-design.md 是文字规格的极限（437 行仍描述不了「感觉」）；你给的段间距数据（0.6/0.3/0.7cm）是数字规格的胜利；README 原型是 B 的实例。

### 2.2 参考物（截图/竞品/网页）要不要作为票的标准附件？

**背景**：你多次说「GitHub 网页手机版」「B站风格」——参考物比文字精确 100 倍，但代理能不能可靠拿到参考物？

**选项展开**：
- **A. 票内嵌参考截图**（你提供或指定 URL，代理抓取）
- **B. 建立「参考库」**（docs/references/：GitHub 网页截图、PiliPlus/gh4a 截图按页面分类）——全局统一参考源
- **C. 只指 URL 不抓图**（代理自己看网页）——依赖代理的网络/理解
- **D. 不引参考**（纯文字规格）——已知失败模式（信息衰减最大）

**联想参照**：rikkahub/PiliPlus/gh4a 已克隆在 ~/dev（§2264）；你在 grill 里给过 ASCII 示意图（长条按钮）——比文字有效得多。

## 六、反馈前置机制

### 6.1 怎么让「你的眼睛」出现在更早的环节？

**背景**：唯一校准点在链路最末端（APK→你）——返工成本最高处。往前移一档都是赚。

**选项展开**：
- **A. 里程碑固定走查**（每 3-4 票合并后你走查一次，无论票大小）
- **B. 关键页面首版即走查**（新页面第一版能跑就给你看，不等全部做完）——原型模式的复用
- **C. 你参与票的「验收标准编写」**（票开工前你过一眼验收标准）——比审规格轻，比事后验收早
- **D. 代理自设「走查点」**（大票中间设 checkpoint 截图给你）

**联想参照**：README 原型 = B 的极致（专做一屏给你看）；T13 云端自审几轮才给你 = D 的失败版（审查完还有 14 问题）。

### 6.2 反馈环与并行度的矛盾怎么平衡？

**背景**：任何需你参与的反馈环都阻塞代理（你在睡/忙时代理停摆）——但完全不等你 = 信息衰减。

**选项展开**：
- **A. 串行波 + 你审批**：一波票做完 → 你走查 → 修 → 下一波（你睡时跑纯逻辑波）
- **B. 并行票但共享「反馈闸门」**：多票并行做，但合 main 前统一过你
- **C. 你只审批「高风险闸门」**（跨页面/全局改动/新交互），单页票代理自主
- **D. 代理把「不确定的」攒起来一次性问你**（问题批量，不逐票打断）

## 十、浪费接受度

### 10.1 哪些浪费必须消除，哪些可以接受？

**背景**：你分析过浪费结构（返工/沉没成本/执行偏差/机会成本）——不是所有浪费都能消除（代理无直觉、体感难文字化）。

**选项展开**（按「接受/消除」分类，逐项表态）：
- **A. 代理执行偏差**——消除手段：验收前置 + 意图复述 + 决策日志（成本：每票多 10-20% 时间）
- **B. 真机返工**——消除手段：里程碑走查 + 原型先行（成本：你的时间）
- **C. 沉没成本（连坐返工）**——消除手段：小步合入 + 模块隔离（成本：合入次数变多）
- **D. 机会成本（错误方向推进）**——消除手段：高风险票先原型/先走查（成本：每票多一轮）
- **E. 一定比例的浪费本身**——接受（如 10-20% 的票需要返工）？还是 0 容忍？

### 10.2 单票的「完成标准」谁来定、怎么定？

**背景**：门禁只验「做了」（编译/测试过）不验「做对了」（符合意图）——「做对」的标准缺失是浪费总根源。

**选项展开**：
- **A. 票体写「验收标准」**（用户视角可执行描述）——每票开工前你过目
